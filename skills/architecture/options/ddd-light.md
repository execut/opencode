# DDD light (ddd-light)
Обязательные опции: нет
Синонимы: предметно-ориентированная разработка, DDD, бизнес-ориентированная разработка.

DDD light - самый облегчённый вариант архитектуры на базе подхода DDD (Domain driven design).
Domain driven design - это подход к разработке, основанный на моделировании реальных бизнес-процессов и их изолировании в слое domain.
Есть только слой domain. Всё остальное находится в прикладном слое и никак не поделено.

## Структура папок

- `<context>/` - папка контекста или реализации приложения
  - `domain/` — папка для доменного (domain) слоя
    - `<aggregate>.go` - агрегат, основная сущность
      - Внутри находятся переменные для ошибок бизнес-инвариантов
    - `<aggregate>_test.go` - тесты для агрегата. Обязательно должен быть live-тест агрегата, покрывающий ПОЛНЫЙ жизненный цикл: создание → изменение состояния → одобрение/отклонение → ... Каждый метод агрегата добавляется в live-тест отдельным шагом (t.Run), а не отдельной тест-функцией (подробнее в скиле tests)
    - `<entity>.go` - (опционально) вложенная в агрегат сущность с названием <entity>
  - `service.go` - прикладной и инфраструктурный слой
  - `service_test.go` - интеграционные тесты прикладного слоя

## Принципы

Любое приложение состоит из слоёв. При разных комбинациях опций, слои могут как соединяться вместе, так и разъединяться.
Они должны быть отдельны, если это указано в архитектурной опции явно.

### Contract

Слой содержит контракты контекста. Ничего не знает про другие слои. Содержит интерфейсы, через которые клиенты общаются с контекстом.

### Application
Прикладной слой. Реализует контракты из предыдущего слоя.

- Знает только про domain-слой
- Оркеструет операции домена: загружает агрегаты через репозитории, вызывает методы агрегатов, сохраняет изменения.
- Определяет контракты команд/сообщений (DTO для входа в приложение).
- Может содержать транзакционную логику, но не бизнес-инварианты.
- Не должен содержать бизнес-логику. Вся бизнес-логика должна быть в domain

#### Unit-тесты
Unit-тесты в прикладном слое запрещены.

Исключение — мапперы ошибок/состояний (перевод `domain.Err...` в `contract.Err...`, маппинг доменных типов в контрактные). Для них допускаются unit-тесты, при условии что маппер выделен в отдельную структуру с публичными методами (например, `errors.go` с типом `Mapper` и методами `Map(err error) error`). Покрытие маппера осуществляется unit-тестами этой структуры, а НЕ прогоном бизнес-ошибок через весь сервис в интеграционном тесте.

#### Интеграционные тесты

Интеграционный тест прикладного слоя называется service_test.go
- В интеграционных тестах запрещено использовать моки. Они должны использовать БД напрямую
- application-слой должен тестироваться линейными интеграционными, короткими тестами
  - Запрещено тестировать разветвлённую логику. Это сигнал, что в прикладной слой перетекла бизнес-логика. В случае, если в прикладном слое есть разветвления, их нужно переносить в бизнес-слой и там тестировать 
- В тестах прикладного слоя запрещено тестировать бизнес-логику. Только её интеграцию в прикладной слой
- Основной сквозной тест прикладного слоя — единый live-тест жизненного цикла агрегата через контракт (create → get → update → approve → ...), шаги которого покрывают методы. Отдельные тест-функции на каждый метод без общего жизненного цикла — нарушение: вместо них должен быть один live-тест с последовательными шагами.
  - Ветки логики для ошибок ЗАПРЕЩЕНО тестировать для повышения эффективности тестов
- Интеграционный тест должен тестировать ровно столько, сколько нужно, чтобы проверить интеграцию domain с прикладным слоем и инфраструктурой. Всё остальное должно быть в unit-тестах domain
- Прикладной слой тестируется только интеграционно через публичный контракт приложения. Unit-тесты прикладного слоя запрещены. Mockgen-моки (и tests_common) применяются только для доменных объектов при наличии инфраструктурных зависимостей; для прикладного слоя моки репозиториев не используются — его поведение покрывается интеграционными тестами с реальным хранилищем.
- Smoke-тесты разрешены только для НЕ реализованных (stub) методов. После реализации — вызов из smoke удаляется, покрытие через live-тест
- Общее правило DI/моков из tests.md применяется ТОЛЬКО к доменным объектам; для прикладного слоя DI-опции для репозитория в тестах не используются.
- Прикладной слой нельзя делать “мокаемым” (нет WithProductRepository для тестов, нет tests_common/моков рядом с сервисом).
- Если ошибка уже проверена в unit-тесте домена (domain/*_test.go) или unit-тесте маппера — ЗАПРЕЩЕНО проверять её в интеграционном тесте. Одна ошибка тестируется ровно один раз, на своём уровне.
- Прогон бизнес-ошибки через реальную БД в интеграционном тесте НЕ является «проверкой интеграции»: маппинг домен→contract уже покрыт unit-тестом маппера, поведение агрегата — unit-тестом домена.

Примеры запрещённых и разрешённых интеграционных тестов прикладного слоя:

НЕПРАВИЛЬНО и ЗАПРЕЩЕНО (дублирует unit-тесты domain, проверяет только тривиальный маппинг ошибок валидации):
```go
require.ErrorIs(t, err, contract.ErrProductNameNotChanged)   // доменная, тестируется в domain/product_test.go
require.ErrorIs(t, err, contract.ErrProductAlreadyApproved)  // доменная
require.ErrorIs(t, err, contract.ErrInvalidProductID)        // валидация, тестируется в domain/product_id_test.go
require.ErrorIs(t, err, contract.ErrProductAlreadyDeleted)   // доменная
```

ПРАВИЛЬНО и РАЗРЕШЕНО (ошибка инфраструктуры, проверяемая только косвенно через прикладной слой):
```go
require.ErrorIs(t, err, contract.ErrProductAlreadyExists)
require.ErrorIs(t, err, contract.ErrProductNotFound)        // ошибка хранилища (RowsAffected==0)
require.ErrorIs(t, err, contract.ErrProductAlreadyExists)   // ошибка хранилища (23505)
```


Интеграционный тестирует прикладной слой через публичный контракт (contract.Application),
используя реальную БД. Поскольку вызовы идут по цепочке contract → service → repository → DB,
репозиторий покрывается тестами КОСВЕННО — отдельные тесты репозитория не нужны.

Именно интеграционные тесты в `service_test.go` (а не прямые тесты репозитория)
обеспечивают покрытие кода репозитория для метрики покрытия.

#### Ошибки в интеграционных тестах

В интеграционных тестах ЗАПРЕЩЕНО тестировать любые ошибки, кроме перечисленных ниже.
Разрешённые ошибки — только те, что возникают на границе с хранилищем:

| Тип ошибки | Примеры | Где покрывается | Интегр. тест? |
|---|---|---|---|
| Ошибки хранилища | ErrProductNotFound, ErrProductAlreadyExists, ErrProductAlreadyChanged | Только косвенно через service | ✅ Да |
| Доменные бизнес-правила | ErrProductNameNotChanged, ErrProductAlreadyApproved, ErrProductAlreadyRejected, ErrProductInvalidPrice | Unit-тесты domain | ❌ Нет |
| Ошибки валидации | ErrInvalidProductID, ErrProductNameRequired | Unit-тесты domain / VO | ❌ Нет |

Простое правило: если ошибка может возникнуть ТОЛЬКО в результате SQL-запроса
(23505, ErrNoRows, RowsAffected==0 в WHERE) — её можно тестировать в интеграции.
Если ошибка возвращается методом агрегата до SQL-запроса — она уже покрыта
unit-тестами domain, её запрещено тестировать в интерационном тесте, поскольку она дублируется в unit-тестах.

- Для каждого метода прикладного слоя пишется один сквозной happy-path тест.
  Ветки ошибок в интеграционных тестах запрещены, кроме ошибок хранилища,
  которые невозможно проверить иначе.


### Обязательный live-тест прикладного слоя

Основным интеграционным тестом прикладного слоя (service_test.go) является
ОБЯЗАТЕЛЬНЫЙ live-тест жизненного цикла агрегата через публичный контракт
приложения (contract.Application): создание → чтение → изменение состояния →
история событий → удаление и т.д. Шаги оформляются последовательными t.Run()
и переиспользуют одну сущность (см. раздел «Тест жизненного цикла сущностей»).

Отдельные тесты на методы допустимы только КАК ДОПОЛНЕНИЕ к live-тесту
(для специфичных кейсов: ошибки хранилища и т.п.), но не вместо него.
Наличие live-теста — обязательное условие приёмки интеграционного теста.

### Domain
**Синонимы**: domain-слой, предметный-слой, бизнес-слой

В этом слое находится модель предметной области, она моделирует реальные бизнес-процессы, их правила и логику.
Тут находится бизнес-модель и её объекты.

- Не зависит от других слоёв и частей приложения, кроме pkg и библиотек вроде lo
- Вся бизнес-валидация и инварианты находятся здесь.
- Все объекты в domain должны создаваться только через конструкторы для того, чтобы объект мог гарантировать свою целостность.
  В случае ошибки, конструктор возвращает ошибку валидации
- Минимизируйте побочные эффекты в domain: операции возвращают ошибки и генерируют события, но не выполняют I/O.
- Все ошибки должны быть объявлены в переменных с префиксом Err
- Слой ничего не знает про БД и про её реализацию. Не должно быть специальных конструкторов под БД.
- Все бизнес-типы должны жить в domain, а не импортироваться из внешних слоёв (contract/infrastructure).
- Если contract и domain используют одни и те же понятия, их нужно определить в domain и маппить в contract на границе.
  - `application` сам импортирует типы из `domain` и мапит их в `contract`.
- Запрещён импорт из других слоёв в domain

#### Unit-тесты
- В domain весь функционал необходимо обязательно покрывать unit-тестами.
- Тест агрегата `<aggregate>_test.go` — это ОБЯЗАТЕЛЬНЫЙ live-тест полного жизненного цикла (create → update → approve → ...), шаги оформляются последовательными t.Run() без t.Parallel() внутри, с переиспользованием одной сущности. Отдельные параллельные проверки допустимы только КАК ДОПОЛНЕНИЕ к live-тесту (валидация, ошибки), но сам live-тест обязателен.

### Обязательный unit-live-тест доменного агрегата

Live-тест жизненного цикла обязателен НЕ только для прикладного слоя, но и для
каждого доменного агрегата на уровне unit-тестов. В `<aggregate>_test.go` домена
должен существовать ОДИН lifecycle-тест (например `TestProductLifecycle`) с
последовательными `t.Run`-шагами, которые переиспользуют одну сущность:
create → чтение полей → каждое изменение состояния (rename/approve/reject/…) →
проверка версии и событий. Шаги оформляются по правилам раздела
«Тест жизненного цикла сущностей» (без `t.Parallel()` внутри шагов).

Требование распространяется на оба уровня:
- доменный агрегат — unit-live-тест в `app/.../domain/<aggregate>_test.go`;
- прикладной слой — integration-live-тест в `service_test.go`.

Новые методы агрегата (в рамках новых задач) добавляются ШАГОМ в существующий
unit-live-тест ПОСЛЕ предыдущих шагов, переиспользуя состояние, созданное ими.
Запрещено выносить happy-path методов агрегата в отдельные тест-функции
(`TestProductUpdateName`, `TestProductApprove` и т.п.) — вместо этого они
становятся шагами единого unit-live-теста. Если в `<aggregate>_test.go` нет
функции с последовательными шагами одной сущности — unit-тест домена считается
невыполненным. Набор независимых параллельных подтестов
(на проверку валидации, ошибок и граничных случаев) допускается только КАК
ДОПОЛНЕНИЕ к unit-live-тесту, но не вместо него.

#### Интеграционные тесты
Интеграционные тесты в domain-слое запрещены, потому что этот слой не должен быть зависим от инфраструктуры

#### Вспомогательный поддомен
Вспомогательный поддомен необходим для того, чтобы моделировать бизнес-логику, строящуюся вокруг основного бизнес-слоя.
Примеры вспомогательного поддомена:
- Подписчик на бизнес-события для их интеграции в другой контекст
- Подписчик на бизнес-события для их ретрансляции в outbox или систему событий
- Бизнес-модель операции чтения

#### Сущности
**Сущность (Entity)** - это объект с идентичностью (например, Product, Promotion). Моделирует бизнес-объект из реального мира.
**Агрегат (Aggregate)** - группа сущностей и VO с корнем-агрегатом (Aggregate Root) — единственная точка входа для команд. Только через агрегаты команды меняют состояние контекста.
- Пишите мелкие, понятные методы в агрегате. Сложную кросс-агрегатную логику выносите в Domain Service или Application.
- receiver-ы сущностей должны быть только указателями. Сущности запрещено передавать по значению. Везде используй указатели
- Бизнес-инварианты агрегата должны проверяться внутри самого агрегата.
  Если действие пытается перевести агрегат в неконсистентное состояние, метод агрегата должен вернуть бизнес-ошибку из domain, а не булевый флаг.
  Application layer не должен самостоятельно интерпретировать состояние агрегата и выбирать бизнес-ошибку.
- Импорт contract в domain запрещён
- Бизнес-ошибки объявляются в domain, а не импортируются из contract.
- Все бизнес-ошибки должны мапиться из domain слоя в contract на прикладном уровне. Прикладной слой мапит domain.Err... в contract.Err....
- Прикладной слой выполняет только координацию (вызовы репозитория и методов агрегата). Вся бизнес-логика — строго в domain.
- Вся бизнес-логика должна быть реализована в методах доменного агрегата (или сущности). Прикладной слой (service.go) выполняет только координацию: вызывает методы репозитория и методы агрегата, но не содержит бизнес-логики (вычислений, проверок, принятия решений).

#### Объекты-значения
**Объекты-значения (Value Object или VO)** - неизменяемый объект, сравниваемый по значению (Price, SKU). Моделирует существительное.

- VO являются неизменяемыми. Если возникает необходимость поменять объект, то это другой объект, его необходимо копировать.
- Копироваться VO должны только через специальные методы-фабрики внутри VO.
- Свойства VO должны быть публичными для упрощения доступа и кода, но эти свойства нельзя менять извне.
- Все ID тоже должны быть VO. Тем самым они инкапсулируют в себе свою реализацию
  - Если ID можно выразить как бизнес-объект и контекст это позволяет, то его нужно называть в виде существительного. Например: не UserID, а User.
  - Такие VO должны обеспечивать правильность значения ID в конструкторе. В таких случаях можно заносить библиотеки, которые отвечают за UUID

#### Предметные сервисы
Предметные сервисы (Domain Service) - это бизнес-логика, которая не относится к сущности/агрегату и относящаяся к домену.

#### Repository
Интерфейс для загрузки/сохранения агрегата.

### Infrastructure
Инфраструктурный слой - это технический фундамент приложения, который обеспечивает связь доменной модели с внешним миром.

Он берет на себя все детали реализации, позволяя основному коду (домену) концентрироваться исключительно на бизнес-логике.
В инфраструктурном слое находятся:
- Реализация репозиториев, интерфейсы которых объявлены в домене
- Реализация интерфейсов для взаимодействия с внешними сервисами
- Знает только про слой domain

### Presentation
Слой представления - это реализация клиентов приложения. Тут находятся:
- Хандлеры для обработки внешних событий
- Консольные приложения

Слой presentation должен знать только про слой contract.

## В комбинации с другими опциями
### repository

В структуре появляются ещё файлы:

- `<context>/`
  - `domain/`
    - `repository.go` - интерфейс репозитория агрегата. Содержит в аргументах и возвращаемых значениях только структуры из domain.
    - `<entity>_repository.go` - (опционально) репозиторий сущности с названием <entity>
  - `repository.go` - реализация репозитория из интерфейса в domain
  - `<entity>_repository.go` - (опционально) реализация репозитория сущности с названием <entity>
