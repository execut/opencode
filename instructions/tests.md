# Правила написания unit и интеграционных тестов

Использовать при написании любых тестов

- Каждый тест должен придерживаться паттерна AAA.
    - Каждый тест должен состоять из трёх блоков, резделённых переносами:
        - Подготовка (arrange) - подготовка тестовых данных, моков и тестируемого объекта
        - Действие (act) - вызов тестируемого метода
        - Проверка (assert) - проверка
    - Пример теста по паттерну AAA (комментарии в тесте не нужно делать, они для пояснения):

```go
    t.Run("success", func (t *testing.T) {
// подготовка
t.Parallel()
id := uuid.New()

// действие
product, err := domain.NewProduct(id, "Coffee")

// проверка
require.NoError(t, err)
require.Equal(t, id.String(), product.ID())
require.Equal(t, "Coffee", product.Name())
})
```

- Результаты должны проверяться через библиотеку github.com/stretchr/testify
- Отдельная тест-функция — имя по объекту/контракту (например TestProductHistory, TestCreateProduct), без when_..._then_... в имени функции.
- Подтест (t.Run) — ТОЛЬКО здесь применяется паттерн when_ДЕЙСТВИЕ_then_ОПИСАНИЕ_РЕЗУЛЬТАТА.
  - Все подтесты должны называться согласно паттерну "when_ДЕЙСТВИЕ_then_ОПИСАНИЕ_РЕЗУЛЬТАТА"
  - Если подтестов нет, то нельзя склеивать имя отдельной тест-функции с when_..._then_... (не создавать TestXxx_when_yyy_then_zzz как имя функции). Достаточно просто имени основной функции
- Привести примеры корректного (функция TestProductHistory + подтест when_invalid_id_then_error) и некорректного (TestProductHistory_when_invalid_id_then_error) вариантов.
- Все тесты должны быть параллельны за счёт конструкции `t.Parallel()`, кроме последовательных тестов жизненного цикла
  сущностей
- Тесты должны быть в отдельном package, названном согласно паттерну `<package>_test`, где `<package>` - название пакета
  тестируемого объекта
- Каждый файл тестов должен тестировать один объект. Название теста должно соответствовать паттерну
  `<object_file>_test.go`, где `<object_file>` - название файла тестируемого объекта
- Общий код по тестам нужно собирать в файле tests_common/common.go Тестовые данные необходимо собирать там в переменных
  с префиксом test.
- Тестовые конструкторы необходимо называть с префиксом NewTest, чтобы их отличить от других конструкторов.
- Для моков необходимо всегда использовать библиотеку go.uber.org/mock/mockgen
    - Каждый мок генерировать нужно только через директиву //go:generate в начале теста, где нужен мок.
    - Моки нужно складывать в папке tests_common/mocks/
- Каждый тест должен тестировать только один случай
- Проверки выполняются через `github.com/stretchr/testify`.
- Каждый файл тестов должен тестировать только один контракт\объект
- Если в одной папке лежат unit- и интеграционные тесты одного объекта, ОБЯЗАТЕЛЬНО использовать постфиксы: *_
  unit_test.go (unit) и *_integration_test.go (интеграционный)

## Тест жизненного цикла сущностей

Тест жизненного цикла сущности нужно писать, когда необходимо проверить один связный сценарий работы с одной сущностью
через контракт объекта (приложения или тестируемого агрегата): создание, чтение, изменение состояния, историю событий,
удаление или другие последовательные этапы.

Такой тест подходит для интеграционных и unit-тестов, где каждый следующий шаг опирается на состояние, созданное
предыдущим шагом. Не нужно использовать lifecycle-тест для независимых проверок валидации, ошибок, граничных случаев или
набора однотипных кейсов: такие сценарии должны оставаться отдельными параллельными тестами или table-driven тестами.

### Правила написания lifecycle-теста

- Подтесты нужно называть не через паттерн как в основных правилах. В названии в snake_case нужно писать кратко описание
  проверяемого этапа жизненного цикла сущности. Например: "create", "approve", "create_and_autoapprove"
- В рамках одного теста должна проверяться одна сущность или один агрегат
- Создавать в каждом подтесте экземпляры тестируемого объекта запрещено! Lifecycle-шаги обязаны работать с ОДНИМ
  экземпляром, созданным в скоупе основного теста; создание нового экземпляра внутри шага — нарушение.
    - Исключение - если для тестового случая требуется создать второй экземпляр
- Приложение, контекст, идентификаторы сущности и общая подготовка создаются один раз в начале теста.
- Очистка данных выполняется один раз через `t.Cleanup()`.
- Внутри шагов жизненного цикла не нужно вызывать `t.Parallel()`, потому что шаги должны выполняться последовательно и
  переиспользовать состояние одной сущности.
- Родительский lifecycle-тест может вызывать `t.Parallel()`, если он полностью изолирован от других тестов: использует
  уникальные идентификаторы и не выполняет глобальную очистку общих таблиц или хранилищ.
- Каждый шаг должен сохранять структуру ACT: подготовка для конкретного шага, действие, проверка. Общую подготовку, уже
  выполненную в начале lifecycle-теста, не нужно дублировать в каждом шаге.
- Live-тест жизненного цикла агрегата должен РАСТИ вместе с агрегатом: при добавлении нового метода агрегата (в рамках
  новых задач) его happy-path сценарий добавляется ШАГОМ (t.Run) в существующий live-тест ПОСЛЕ предыдущих шагов,
  переиспользуя состояние, созданное ими. Запрещено выносить методы агрегата в отдельные тест-функции
  (TestProductUpdateName, TestProductApprove и т.п.) — вместо этого они становятся шагами единого lifecycle-теста.
- Набор независимых параллельных подтестов (t.Parallel () в каждом) в файле теста агрегата НЕ заменяет live-тест.
  Live-тест жизненного цикла обязателен для каждого агрегата: если в `<aggregate>_test.go` нет функции с
  последовательными шагами одной сущности — тест считается невыполненным.
- Негативные ветки/валидацию при необходимости нужно писать в отдельные test-функции в дополнение к live-тесту

## Классификация тестов

Перед написанием ЛЮБОГО теста определи его тип:

1. Проверяется значение/ошибка, порождаемая бизнес-логикой объекта (методом, который не выполняет обращение к
   хранилищу/инфраструктуре) → unit-тест этого объекта, в той же папке.
2. Проверяется значение/ошибка, порождаемая хранилищем (уникальность, отсутствие строки, конфликт версии — приходит
   только из SQL-запроса) → интеграционный тест через публичный контракт приложения.
3. Проверка смены статуса, причин одобрения/отклонения, автоодобрения, сброса модерации — это бизнес-логика объекта. Её
   место — unit-тесты. В интеграционных тестах такие переходы допускаются ТОЛЬКО как happy-path шаги единого live-теста
   жизненного цикла, но не как отдельные test-функции и не с проверкой негативных веток.
4. Следующие сценарии — это бизнес-логика объекта, а не работа хранилища. Их место — unit-тесты объекта; в
   интеграционных тестах они допустимы ТОЛЬКО как happy-path шаги единого live-теста жизненного цикла, но НЕ как
   отдельные test-функции и НЕ с негативными ветками:

- авто-переходы по правилам;
- сброс состояния при изменении полей;
- переходы жизненного цикла;
- нормализация и валидация входных значений;
- вычисляемые значения (флаги, причины, производные поля), порождаемые правилом до обращения к хранилищу.

### Unit-тесты

- Файл unit-теста должен лежать в той же папке, что и тестируемый объект
- Запрещено вручную писать структуры-стабы/фейки, реализующие инфраструктурные зависимости (репозитории), вместо
  сгенерированных mockgen-моков.
- Для инфраструктурных зависимостей конструктор тестируемого объекта должен принимать интерфейсы или предоставлять опции
  конструктора, чтобы unit-тесты во внешнем пакете <package>_test могли внедрять моки. Запрещено создавать
  инфраструктурные зависимости внутри конструктора без возможности их подменить в тесте.
- Интерфейсы, которые мокаются в unit-тестах, должны быть экспортированными (например ProductRepository).
  Сгенерированный mockgen-мок живёт в отдельном пакете tests_common/mocks/, который импортирует исходный пакет, поэтому
  неэкспортируемый интерфейс там недоступен.
- Если объект нельзя протестировать unit-тестом во внешнем пакете с mockgen-моками (нужен доступ к неэкспортируемым
  полям, порты не экспортируются, нет DI) — это сигнал о проблеме проектирования, а не повод писать стабы. Требуется
  вынести мокаемую зависимость наружу и добавить тестовую инъекцию.

### Интеграционные тесты

Интеграционными называют такие тесты, которые ничего не мокают и тестируют интеграцию структуры с инфраструктурой.

При написании интеграционных тестов (не unit-тестов) нужно в обязательном порядке придерживаться следующих правил:
- Должен быть единый lifecycle-тест для happy-path состояния приложения. В таких тестах проверяется интеграция инфраструктуры с приложением.
- В интеграционных тестах один метод должен тестироваться ровно один раз, исключая:
  - Вызовы пишущих методов для предварительной подготовки состояния приложения, чтобы протестировать другой метод (этот другой метод тоже должен быть вызван только один раз)
  - Вызовы читающих методов для проверки состояния приложения после его изменения
  - Если используется архитектурный подход, где моки запрещены и бизнес-логику невозможно протестировать без интеграционных тестов
  - Тесты ошибок, порождаемых хранилищем (дубликат, отсутствие записи, конфликт версии)
    - Тесты других ошибок запрещены!
- Табличные тесты запрещены
- При добавлении поля в команду (например, CreateProduct получает category/price) его нужно добавить в существующий live-тест. Отдельная test-функция на каждое поле — нарушение.
  - Например: шаг create передаёт все поля, шаг get их проверяет.
- Запрещено подглядывать или смотреть в приёмочные тесты при написании компонентных тестов. При написании интеграционных тестов должны закладываться принципы написания интеграционных тестов, а не структура приёмочных.

#### Ошибки в интеграционных тестах

В интеграционных тестах ЗАПРЕЩЕНО тестировать любые ошибки, кроме ошибок, которые порождает хранилище.

| Тип ошибки              | Пример                                                                | Где покрывается        | Интегр. тест? |
|-------------------------|-----------------------------------------------------------------------|------------------------|---------------|
| Ошибки хранилища        | ErrProductNotFound, ErrProductAlreadyExists, ErrProductAlreadyChanged | Косвенно через service | Да            |
| Доменные бизнес-правила | ErrProductNameNotChanged, ErrProductAlreadyApproved                   | Unit-тесты             | Нет           |
| Ошибки валидации        | ErrInvalidProductID, ErrProductNameRequired                           | Unit-тесты             | Нет           |

- Если ошибка возникает ДО обращения к хранилищу (её возвращает бизнес-логика объекта) — тестировать её в интеграционном
  тесте ЗАПРЕЩЕНО. Это дублирование unit-тестов.
    - В service_test.go разрешено использовать require.ErrorIs ТОЛЬКО с ошибками, которые порождаются на
      инфраструктурном уровне: ErrProductNotFound, ErrProductAlreadyExists, ErrProductAlreadyChanged. Любая другая
      ошибка (доменная, валидации, бизнес-правило) — нарушение, приводящее к отклонению задачи. Если ошибка не из белого
      списка — она уже покрыта unit-тестом домена/VO/маппера, дублировать её в интеграции запрещено.
    - Контрольная фраза: «эта ошибка приходит из хранилища? → интеграционный тест. Эта ошибка вычисляется бизнес-логикой
      до хранилища? → unit-тест.»

#### Что допустимо утверждать в интеграционном тесте

Интеграционный тест (кроме интеграционного live-теста) проверяет интеграцию предметного слоя с инфраструктурой, а не
бизнес-поведение. Допустимы ровно два класса утверждений:

| Класс                             | Пример (обезличенный)                                            | Разрешено                            |
|-----------------------------------|------------------------------------------------------------------|--------------------------------------|
| Ошибка хранилища                  | «запись не найдена», «дубликат», «конфликт версии»               | ✅                                   |
| Чтение/фильтр/пагинация/агрегация | выборка по статусу/периоду, поиск по подстроке                   | ✅                                   |
| Бизнес-переход/значение           | итоговый статус после правила, вычисленное поле, сброс состояния | ❌ (unit / интеграционный live-тест) |

Приёмочные тесты намеренно проверяют бизнес-логику сквозь весь стек. Внутренний интеграционный тест НЕ должен зеркалить
их структуру: «один контрактный кейс ≠ одна интеграционная test-функция».
